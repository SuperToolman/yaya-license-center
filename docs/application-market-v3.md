# 应用市场 V3：单应用与套应用

单应用和套应用使用同一个不可变发布包。系统从用户选择的平等成员集合沿结构化资源引用递归收集必要成员，循环去重；不会收集只反向引用所选成员的其他应用。关联组件（含子表）、自动化、导航、视图、按钮及明细定义均参与校验。来源应用、路径和目标资源会显示在发布确认弹窗中。

## 发布、审核和授权

- `POST /api/apps/{appId}/market-preflight` 返回成员、依赖、资源统计、阻断项及结构指纹。
- `POST /api/apps/{appId}/market-submission` 接收 `fingerprint`、可选 `productId` 和 `newProduct`。结构变化返回冲突，必须重新预检。失败的上传保存元数据和 ZIP，原样重试；运营端相同申请内容幂等，内容不同拒绝覆盖。
- V3 ZIP 包包含 `manifest.json` 与 `bundle.json`，使用逐文件 SHA-256。两端独立验证资源归属、依赖闭合、依赖图与资源一致性及包限制；拒绝旧 V2 包。
- 商品 ID 由运营端生成，绑定发布许可证主体。一个商品可以增加成员，不能移除成员。需要缩减范围时选择“发布为新商品”。
- 审核通过只产生可上架版本。运营通过版本选择显式上架，目录仅展示上架版本。下架或撤销授权不删除客户本地安装。
- 授权按许可证主体与商品生效，下载票据有效期 300 秒，绑定 release、版本和包摘要，只能核销一次。客户端根据票据校验下载包，避免版本切换错配。

## 安装和版本管理

一次安装包含所有成员，每个商品只允许一份安装。整包创建独立应用，不复用客户已有应用。先分配资源 ID，再仅在已知引用字段中重写应用、表单、流程、视图、按钮和导航 ID；业务字段 ID 保留。安装事务同时保存本地版本包，失败整体回滚，自动化默认暂停。

升级完整应用受管理资源，允许新增成员和资源，禁止删除成员、资源、字段以及改变字段类型或关联目标。发现本地结构变化时保守阻止覆盖，需要先解决冲突。回滚同样受这些规则约束，例如新版新增字段后不能回滚到会删除该字段的旧包。它不是数据库备份恢复。

归档、恢复和永久清理针对全部成员；恢复不会自动启动自动化。正常永久清理要求已归档，且逐表检查真实业务记录和流程实例。普通应用删除接口拒绝删除套内单独成员。

外部 HTTP/连接器、凭证、用户权限绑定、固定实例文件或记录引用等不能完整移植的配置会阻止发布。自定义 HTML/TSX 目前无法静态验证其动态资源引用，也会给出定位明确的阻断项。安装者另行配置访问权限。硬编码内部链接需要改成结构化应用/表单目标，不能依赖任意代码字符串替换。

## 显式清空重建

迁移仅新增数据结构，启动和部署不会清理市场。新分发不支持旧包，因此启用前应停止两端写入，备份数据库和包目录，显式执行以下维护命令，再重新发布。

在各自 API 的工作目录，使用对应服务原有数据库配置：

```powershell
cargo run -- --market-reset-preview
cargo run -- --market-reset <预览返回的confirmation>
```

预览展示数据库、包目录、待删表及数量。低代码端还展示待删除的安装应用和业务记录数量。确认凭据绑定当前数据与文件内容；变化后必须重新预览。命令在启动服务、执行迁移或恢复后台任务前退出。

运营端删除应用市场商品、版本、上下架、授权、票据及应用包。低代码端删除旧市场安装应用（包括业务数据和流程实例）、市场记录及缓存，保留开发者源应用并重置其市场标识。客户、平台许可证和 AI 员工市场不在清理范围内。数据库提交后删除已核对的包文件；如文件删除失败，修复文件权限后重新预览和执行剩余清理。

## 验证

普通市场单元测试：`cargo test app_market`（低代码端）、`cargo test application_protocol`（运营端）。

跨端测试使用新的 PostgreSQL schema 和临时 SQLite/包目录，不清理开发或正式业务数据：

```powershell
$env:WORKFLOW_TEST_DATABASE_SETTINGS_PATH = '<测试 PostgreSQL 配置文件的绝对路径>'
$env:MARKET_OPERATION_TEST_MANIFEST = '<运营端 api/Cargo.toml 的绝对路径>'
cargo test market_suite_database_and_cross_platform_lifecycle -- --ignored --nocapture
```

测试从真实源表导出循环关联的 A/B/C，调用运营端真实 HTTP 上传、审核、上架、授权及下载，并安装下载结果，检查本地关联、按钮、导航与自动化映射，验证新增第四成员的升级、破坏性回滚阻断、本地修改冲突、升级事务回滚和显式清理。前端另有发布确认弹窗 Vitest 测试、运营审核与上架 Playwright 测试。

## 离线导出与运营导入

“我的应用”的应用操作菜单增加“导出应用包（ZIP）”。确认完整成员、依赖及预检指纹，填写版本号后下载 V3 ZIP；导出不创建上线申请、不修改商品标识，也不需要连接运营服务。导出范围、权限和可移植性检查与在线发布一致，已安装的市场副本不能作为发布源。

`POST /api/apps/{appId}/market-export` 接收 `{fingerprint, version}`，返回 `application/zip` 和 UTF-8 下载文件名。内容使用在线发布的同一打包函数，无业务记录、用户或密钥；服务端重新扫描，结构改变时返回 409。

运营“应用管理 → 导入应用包”选择发布客户及目标商品，上传 ZIP；选择“创建新商品”由运营端分配商品 ID，更新现有商品需要发布客户一致、版本未使用、原有成员全部保留。`POST /api/application-products/import` 接收 multipart 的 `publisherSubject`、可选 `productId` 和 `package`，仅运营身份可调用，发布客户必须存在。ZIP 本身不携带许可证凭证，发布方由运营人员明确指定。

独立校验包结构、摘要和依赖闭合后创建待审核申请；重复导入相同客户、目标及相同字节的包复用申请。导入不自动审核或上架，后续授权和分发沿用正常流程。ZIP 限制与在线上传相同，压缩后不超过 64MiB。

## 自动化依赖的有效配置

发布预检和 ZIP 导出按节点实际模式收集表单：新增、更新、直接删除、查询和发起审批的目标表单会引入其真实所属应用；上游数据来源递归解析来源节点，并校验来源必须在当前节点上游、能输出主表记录且不存在循环。触发数据模式使用自动化的触发表单，不依赖旧表单或节点缓存。成员应用中的所有自动化均参与扫描，包括暂停的自动化。

导出快照会移除新增子表、上游删除及上游/触发查询模式中运行时忽略的旧目标表单缓存，不修改开发者保存的自动化。更新节点即使使用上游数据，也保留并检查 targetFormUuid，防止目标与来源表单不一致。节点和字段 ID 保留，目标应用与表单 ID 按安装映射重写。

运营在线接收、离线导入及客户端安装独立复核相同的自动化协议，拒绝非生效缓存引用、无效节点来源、缺失目标和不支持的节点类型。新增子表还检查父记录来源、主表当前 Schema、子表归属及映射字段有效性和重复映射。收到“非生效的缓存表单引用”错误时应使用当前低代码端重新导出。

预检错误包含应用、自动化 ID、节点 ID 及配置路径；依赖错误不会自动移除必要成员。HTTP/外部连接器及实例凭证、固定用户绑定仍按可移植性规则阻止发布。本检查针对依赖和结构完整性，不替代运行时条件、权限及业务结果验证。

## 成员范围与循环依赖边界

发布范围由本次选择的成员集合沿实际引用方向递归确定，不根据“曾被哪个商品包含”扩展，也不把成员重叠当作重复配置。

| 实际引用关系 | 所选成员 | 必须包含的成员 |
| --- | --- | --- |
| A → B → C，C 无外部引用 | A | A、B、C |
| A → B → C，C 无外部引用 | B | B、C；不包含只引用 B 的 A |
| A → B → C，C 无外部引用 | C | C |
| A → B → C → A | A、B 或 C | A、B、C，循环去重，每个应用仅包含一次 |
| A → B、B → A | B | A、B，以及它们继续引用的全部应用 |

B 曾作为 A 商品的成员，不影响选择 B创建独立商品。不同商品之间允许成员范围相同、包含或部分重叠；相同商品的更新仍须匹配发布主体，禁止删除历史成员。相同申请重试和同商品版本重复检查继续执行。

循环不是阻断理由。只有循环中的必要应用不存在、发布权限不足、成员属于市场安装副本或配置不可移植等情况才阻止发布，不允许通过漏打包成员来绕过检查。运营端同样拒绝缺少循环目标的包。在线发布与 ZIP 导出采用同一规则。

客户分别购买 A 套件和 B 套件时，各商品分别安装整套独立副本，重叠成员不复用、数据不自动共享。包内同一成员出现两次仍属于错误，与商品之间合法重叠是不同情况。
