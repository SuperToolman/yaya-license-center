# 应用市场商业化使用与验收

实施日期：2026-11-16。两端共同使用商品作为销售及整包授权单位。按用户确认，本期复用 AI 员工市场支付弹窗，全部付款、退款、收益和结算都是模拟流程，不接真实资金渠道。

## 发布与上架

1. 开发者从现有上线入口执行依赖预检，确认单应用或套应用的完整成员。
2. 填写商品说明，选择免费或人民币一次买断。收费商品填写整包售价及发布者申请分成；平台分成为余数，运营审核后生效。免费商品价格及分成为零。
3. 提交冻结技术包与商业资料的上线申请。申请重试不能替换商业快照。
4. 运营在“应用管理 → 应用申请管理”查看技术和商业资料并审核。审核通过不会自动上架。
5. 运营显式选择通过审核的发布版本上架，同时采用该版本最新已审核商业配置。
6. 单独调价无需重新打包：发布者在本人商品的“销售配置”提交变更；运营也可补齐商业资料。新商业版本单独审核，重新选择发布版本上架后生效。不会覆盖旧配置或已成交订单。技术审核只涵盖原申请的商业快照，不会顺带批准后续调价。

离线 ZIP 只承载技术资源。运营导入时选择发布客户、商品并填写相同商业资料，进入同一审核流程。缺失商业配置的旧商品不会自动变成免费商品。

## 客户购买与安装

- 已上架且商业资料完整的商品进入客户目录。卡片展示免费或价格、套应用成员及购买状态。
- 免费领取生成已完成的零元订单并自动发放整包权益，不登记回款或收益。
- 收费商品创建待支付订单，使用 AI 员工市场共用支付模态框。点击“测试支付完成”后，服务端以冻结订单价格登记模拟回款、发布者及平台收益，自动开通权益。
- 支付完成后客户自行点击“安装”。同商品每个实例仍只允许一套安装，成员与依赖全部安装，自动化默认暂停。
- “我的订单”可继续支付、关闭待付订单或申请整单模拟退款；“发布者收益”仅返回许可证主体自身的模拟收益。
- 金额以整数分保存，分成以基点保存。发布者金额向下取整，尾差归平台。同一订单重试不会重复回款、发权或入账。
- 买断权益包含同商品后续兼容版本；升级仍执行既有数据安全规则。下架停止新购买，已购客户可下载其成交版本；退款申请期间保留下载权益。
- 发布者继续使用源应用，不能通过自购产生模拟收益。

## 退款、赠送和结算

运营在“应用管理 → 交易与分成”审核退款并登记模拟结算。

- 客户申请退款后，未结算收入冻结，不参与结算。驳回需说明原因并解除冻结；通过后登记整单负向回款及收益冲正。
- 退款只撤销该订单的权益来源。赠送或旧授权仍有效时，客户继续保有权益。下载票据核销时再次检查权益。
- 退款不会删除安装、客户记录或停止本地应用运行。买断使用不要求持续在线验证。
- 已结算收益退款保留负向待抵扣条目；有后续正向净收益时抵扣。结算仅登记模拟批次，不表示银行到账。
- 运营赠送作为独立来源，必须填写原因，记录操作人及审计，不伪造交易。正常领取和购买无需运营分配。
- 通用订单页禁止以通用修改、登记支付或取消接口操作应用订单，避免绕过权益和收益事务。

## 数据与启用

两端 Rust API 需重新编译并重启后使用新接口，前端同步加载新代码。运营 API 启动时幂等创建商业表并将既有权益回填为历史授权；不清理商品、安装、订单或真实客户数据。

已有商品需补齐商业配置、审核并重新显式上架。源应用与其他非应用市场业务保留。

旧市场重置命令默认仍是预览。数据库出现应用订单后，执行重置会被拒绝，避免删除交易关联商品；不能用旧重置命令清除商业历史。

## 模块与契约

- 运营：`api/src/application_commerce.rs`、`application_commerce.sql` 管理商业版本、交易、权益来源、收益冲正及结算事件；复用原订单、回款和不可变技术版本。
- 低代码：`api/src/modules/app_market/commerce.rs` 代理交易，服务端从平台许可证解析主体；安装模块执行整包安装及版本管理。
- OpenAPI、生成客户端及 BFF 同步增加商业变更、订单、模拟支付、退款申请和自身收益接口。客户端不决定成交金额、客户主体或实际分成。
- 本期不实现真实支付签名、渠道查单、实际退款或打款、部分退款、订阅与多作者分账。以后接入真实支付时另行实现，不把模拟流水当成资金凭证。

## 验证范围

- Rust：免费领取幂等、成交快照、重复模拟支付、价格变化、越权拒绝、付款失败事务回滚、商业审核与上架分离、退款冻结/冲正、独立赠送保留、下架目录可见性、重置保护。
- 前端：发布资料校验、共用支付弹窗、购买后安装、免费领取、运营商业审核及模拟退款/结算。
- 隔离数据库跨端：A→B→C 导出，经运营接收、审核、上架、模拟购买与下载，安装到新本地 ID，验证表单及自动化引用重写、业务查询、升级/回滚和清理保护。
- 验证不创建真实收费、不清理真实环境；具体命令与最终结果见交付说明。

## 成员范围与循环依赖边界

发布范围由本次选择的成员集合沿实际引用方向递归确定，不根据“曾被哪个商品包含”扩展，也不把成员重叠当作重复配置。

| 实际引用关系 | 所选成员 | 必须包含的成员 |
| --- | --- | --- |
| A → B → C，C 无外部引用 | A | A、B、C |
| A → B → C，C 无外部引用 | B | B、C；不包含只引用 B 的 A |
| A → B → C，C 无外部引用 | C | C |
| A → B → C → A | A、B 或 C | A、B、C，循环去重，每个应用仅包含一次 |
| A → B、B → A | B | A、B，以及它们继续引用的全部应用 |

B 曾作为 A 商品的成员，不影响选择 B创建独立商品。不同商品之间允许成员范围相同、包含或部分重叠；相同商品的更新仍须匹配发布主体，禁止删除历史成员。相同申请重试和同商品版本重复检查继续执行。

循环不是阻断理由。只有循环中的必要应用不存在、发布权限不足、成员属于市场安装副本或配置不可移植等情况才阻止发布，不允许通过漏打包成员来绕过检查。运营端同样拒绝缺少循环目标的包。在线发布与 ZIP 导出采用同一规则。

客户分别购买 A 套件和 B 套件时，各商品分别安装整套独立副本，重叠成员不复用、数据不自动共享。包内同一成员出现两次仍属于错误，与商品之间合法重叠是不同情况。

## 应用分组与套应用名称

“我的应用”分为本地应用和线上应用。本地应用包含开发者源应用，发布过商品不会改变其归属。线上应用展示已安装的市场商品：单应用归入“购买应用”，使用原应用名称；套应用按商品名称独立分组，组内保留各成员应用名称。购买或免费领取后，需要完成安装才会出现在这里。

上线申请与 ZIP 导出使用同一个预检确认框；套应用须填写 1–80 字的套应用名称，单应用沿用源应用名称。名称写入 V3 包的 `packageName`，运营接收或离线导入时校验并保存，显式上架使用所选版本名称，客户安装后使用已安装版本名称分组。旧格式不兼容，须重新导出。

分组身份使用安装编号，不按名称或成员源编号合并。两个商品即使同名或都包含 B、C，也分别展示各自安装副本；升级、归档等操作仍以各自整包为单位。成员不允许在普通应用入口单独删除，本地列表加载不等待运营同步。

## 平等成员与发布范围

应用包只有成员，没有主应用。确认框可选择任意一个或多个本地源应用，并自动递归收集它们的必要依赖。所有成员统一发布、购买、安装、升级与分组，成员顺序不产生特殊身份。单应用沿用该成员的名称；多成员必须填写套应用名称。

卡片点击只预选该应用，可在选择其他成员后取消。被其他成员引用的必要依赖不可排除。范围变化立即重新预检，保留已填写的销售资料；权限、可移植性与引用完整性校验覆盖全部成员。重复或重叠商品仍分别安装独立副本。

包和请求使用必填的 `selectedAppIds`，成员集合排序去重后纳入指纹，提交和导出重新扫描。两端校验所有选定成员都在包内，实际依赖图与资源一致，全部成员都由选择集合及其依赖组成。新增格式不接受旧主应用字段，也不读取旧包作为安装、升级或回滚目标。旧包必须重新导出。

商品以商品 ID 和发布许可证主体识别，后续版本不绑定某个成员，但仍禁止移除历史成员。安装响应返回全部 `memberAppIds`，没有默认打开的应用。安装表和商品表中废弃的主应用字段直接移除。
